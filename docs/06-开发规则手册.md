# 06 · 开发规则手册

> 违反"硬规则"标注 ⚠️ 的条目会直接伤害演示或队友，其余是强烈建议。

## 1. Git 工作流

- `main` 分支保持随时可跑（⚠️ 禁止在 main 上直接写功能代码）。
- 功能分支命名：`feat/m1-extract`、`fix/sse-断流` 这类"类型/里程碑-内容"。
- 合并：本地完成 + pytest 绿 → 自己 rebase 到最新 main → 合并（组内两人以上时请另一人看一眼 diff）。
- 提交信息格式：`类型: 描述`，类型 = feat / fix / docs / test / refactor / chore。例：`feat: ①抽取流水线接入 DeepSeek`。小步提交，一次提交做一件事。

## 2. 代码规范

- 公开函数一律类型注解 + 一行 docstring 说明输入输出。
- 模块超过 ~300 行考虑拆分（先在组内说一声）。
- 注释写"为什么"，不写"这行在干嘛"；中文注释允许。
- 契约（schemas.py）字段改动必须群通知 + 同步更新 02-架构设计。
- 业务逻辑禁止写在 server.py（路由层只做协议转换）。

## 3. LLM 调用纪律 ⚠️

- 流水线内 temperature=0 全局生效，不许局部调高。
- 所有 LLM 调用必须过 store.py 缓存（按输入哈希）；绕过缓存直接调用模型的代码不许合入。
- 多 Agent 链：轮数上限写死在代码常量里（辩论 ≤ 2 轮），不许靠提示词"劝"模型收敛。
- 演示前一周：冻结 requirements.lock、冻结模型名、冻结演示输入。

## 4. 测试

- pipeline 每个函数至少 1 条 happy-path pytest（固定输入 → 断言输出字段存在且类型正确）。
- 契约变更时同步改 tests。
- `pytest` 绿是合并的前提。

## 5. 工作区卫生 ⚠️（硬规则）

- **每轮工作结束前，必须删除生命周期已结束的临时文件**：调试脚本、一次性数据转换中间产物、下载的临时压缩包、过期截图、试跑产生的杂散输出文件等。判断标准：下次开工还用不用？不用就删。
- `.env`、`db/*.db`、`__pycache__`、`.venv` 依赖 .gitignore 挡在仓库外，不算临时文件，但本地磁盘也要定期清理（`db/` 下重置即删文件）。
- 拿不准的"可能还要用"文件：放进 `tmp/`（已 gitignore）并注明日期，超过 7 天未动自动视为垃圾，下次清理时删除。
- 合并分支前 `git status` 必须干净——没有 untracked 的临时文件混进来。

## 6. 数据纪律 ⚠️

- 每条入库 JD 必须带 `url` 或来源说明（"真实数据与证据"10 分的根基）。
- 不编造数据；语料里的个人信息（HR 名字/电话）入库前抹掉。

## 7. 依赖纪律 ⚠️

- 新增第三方包 = 先在 05 文档登记用途 + 组内同意。
- 以 `requirements.lock.txt` 为准安装；随手 `pip install` 新版本导致环境漂移是事故。

## 8. 记录留档 ⚠️（硬规则）

- **每轮开发、测试、review 结束当天**，必须在 `docs/logs/` 落一篇记录（模板见 logs/README.md）。**没有记录 = 这轮工作没发生**——出事回溯（谁引入、为什么这么改）和课程"系统测试与动态改进"15 分全靠它。
- 记录**只增不改**：写错了新开一篇更正，不改旧文件。
- 篇幅 ≤ 20 行、5 分钟写完；细节放代码与提交信息里，日志只记"何时/谁/做了什么/发现了什么"。
- 双簿不重复记账：`docs/logs/` 放详细过程；04-进度状态的"测试轮留痕"表只登记一行摘要 + 日志文件名。
- 日志结尾必须清点临时文件（与 §5 联动）：已清理 / 无产生。

> 本手册 Owner：项目负责；新增规则直接加条目并更新变更说明。
