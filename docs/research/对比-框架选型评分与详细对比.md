# Agent 框架选型：加权评分与详细对比（完整重写版）

> 取代此前所有对比版本。数据截至 2026-10-24（GitHub Releases 实查）。
> 前提：FastAPI 后端已定；公共底座（数据源接口 / ①~④流水线 / Pydantic 契约 / SQLite）与框架无关，换框架迁移成本 ≈ 1 天。
> 参评：**OpenAI Agents SDK（OAI）｜PydanticAI（PAI）｜LangChain/LangGraph（LC）｜Claude Agent SDK（CAS）**

---

## 一、排序是怎么来的：先定权重，再打分，最后算总分

### 1.1 权重的来源（不是拍脑袋）

三句话推出九个维度：**老师评分表**（技术实现 25 / 真实数据 10 / 测试与改进 15 / 汇报 15 / 思考 35）说明技术要"稳、快、可演示"；**项目形态**（单 Agent 四工具 + 全结构化流水线 + SSE 流式 + SQLite + 国产模型 + 可能的小规模多 Agent + 可能接 MCP 搜索实时资讯）决定哪些能力是刚需；**组况**（5 人学生团队、约两周、部分依赖中文教程和 AI 辅助写码）决定上手成本和踩坑成本的权重。

| # | 维度 | 权重 | 为什么是这个权重 |
|---|---|---|---|
| 1 | 结构化输出可靠度 | **20** | ①~④流水线全是 JSON 契约，这是全项目命脉；输出不稳项目就废 |
| 2 | 上手与开发效率 | **15** | 两周工期 + 5 人水平参差；含中文资料丰富度、AI 辅助写码通过率 |
| 3 | 国产模型接入顺滑度 | **12** | 只用 DeepSeek/GLM/Qwen 国内 API，接入是每天都要碰的事 |
| 4 | 踩坑与排错成本 | **10** | 课设没有时间深挖框架内部；层薄 = 省命 |
| 5 | 流式与 FastAPI 契合 | **10** | SSE 流式对话是演示的门面 |
| 6 | 多 Agent 支持度 | **10** | "分工 + review + 汇总"计划做成演示的一段（不是核心卖点） |
| 7 | MCP / 插件 / skill 扩展 | **8** | 计划接 Exa MCP 搜索实时岗位资讯（补"数据滞后"短板）；后续功能也可能走 MCP |
| 8 | 会话与状态管理 | **8** | 学生档案 + 对话历史要落 SQLite |
| 9 | 版本稳定性风险 | **7** | 锁版本能缓解，但断层教程/破坏性变更仍浪费时间 |

### 1.3 总分与排序

| 排名 | 框架 | 加权总分 | 计算 |
|---|---|---|---|
| 1 | **PydanticAI** | **82.4** | 20+10.5+12+8+9+4.8+6+7.2+4.9 |
| 2 | **OAI SDK** | **80.2** | 18+12+8.4+8+9+7.2+7+6.4+4.2 |
| 3 | **LangChain/LangGraph** | **70.6** | 12+9+10.8+5+7+10+6.4+4.8+5.6 |
| 4 | **Claude Agent SDK** | **64.6** | 14+7.5+7.2+5+5+8+8+6.4+3.5 |

**解读一：前两名差距 2.2 分，在打分误差（±2~3 分）以内，统计上打平**——这就是此前写"≈"的原因。
**解读二：分差全部来自可调节的权重**（见第四节敏感性分析），不是"谁碾压谁"。
**解读三：分数是依据公开证据的判断值**（每格依据见上表+第三节），小组完全可以自己调权重重算——矩阵在，改数就行。

## 二、MCP / 插件 / skill 详述（本轮升级为重点维度）

**为什么重要**：计划接入 Exa MCP 让 Agent 能搜索静态语料里没有的最新资讯（如"最近两周某岗位的新招聘趋势"）。这直接回应三个得分点：PPT 第 9 页自述的"数据滞后性"局限、"真实数据与证据分析"10 分、演示的"智能感"。后续如需天气/日历/其他数据源，同样走 MCP。

| 框架 | MCP 接法（以 Exa 为例） | 成熟度 |
|---|---|---|
| CAS | 扩展模型的"本体"：MCP server + 每工具权限策略（always_ask/always_deny）+ MCP Apps | 最深（10 分） |
| PAI | 原生 MCP toolset；MCP Python SDK v2（GA）就是 Pydantic 团队自己维护的 | 最正统（9 分） |
| OAI | 官方 `agents.mcp`（MCPServerStdio / MCPServerStreamableHttp），近三版持续在改 MCP 细节 | 原生（8 分） |
| LC | `langchain.mcp` + FastMCP（v1.4 起）；注意 MCP 适配器 2.0 是破坏性升级，教程新旧混杂 | 原生适配器（8 分） |

**实操提醒（本对话亲测）**：Exa MCP 免费档有速率限制（连续搜索会被限流）。所以：MCP 搜索结果也要进 SQLite 缓存；演示脚本里"实时搜索"环节要么提前触发过一次、要么准备录播兜底。
**skill/插件体系**：只有 CAS（plugins/skills）和 PAI（Harness 的 Skills capability，可分层项目/个人技能库）有正式概念；OAI/LC 没有对应物，等效做法是"普通工具函数 + 提示词文件"，对课设完全够用。

## 三、逐维度详细说明（给分理由的证据）

### 3.1 结构化输出（权重 20）
- PAI 10 分：输出类型就是 Pydantic 模型，校验失败自动带错误信息重问（内置 retries）；工具参数同样校验。同任务学术评测中代码量最少（52 逻辑行 vs 裸写 31 行）。
- OAI 9 分：`Agent(output_type=...)` 原生；DeepSeek 走 chat completions + 工具调用实测可用（GitHub issue #122 多人验证）。
- LC 6 分：v1.0 `create_agent(response_format=)` 已集成进主循环，但社区有 ToolStrategy+工具在非 OpenAI 模型上组合不稳的报告（官方论坛 v1.0.2），用国产模型必须第一天实测。
- CAS 7 分：SDK 已内置结构化输出（2026-01 API 侧 GA，schema 校验+重试）；扣分在"走 GLM 兼容端点时该特性是否完整实现"未见文档确认。

### 3.2 上手与效率（权重 15）
- OAI 8 分：约 6 个概念；官方文档有简体中文版；学术评测 AI 辅助一次通过率 83%（四家最高）。
- PAI 7 分：开发体验基准 8/10（五框架实测最高）、代码最少；扣分：中文教程最少、v2 太新（2026-06）导致中英教程都滞后、AI 生成代码易过度包装（67% 通过率最低，需人工复核）。
- LC 6 分：中文教程海量是双刃剑——AgentExecutor/create_agent/LangGraph 三代并存，复制粘贴必炸；90 天实测 DX 5/10、工时 41h（对照 PAI 24h）。
- CAS 5 分：权限模式、沙箱、插件、fork 子代理……概念面最大；且社区教程几乎都面向"编码 agent"场景。

### 3.3 国产模型（权重 12）
- PAI 10：DeepSeek / 智谱 Zai / Kimi 三家原生 provider，2026-10 版本刚补齐 Zai/Moonshot 的 base_url 参数。
- LC 9：`ChatOpenAI(base_url=...)` 一行，教程多。
- OAI 7：三行配置可跑，但有两个必踩坑（tracing 默认上传 OpenAI 必关；默认 Responses API 对国产端点 404 必须切 chat_completions）——都是一次性的，配好即忘。
- CAS 6：智谱/Kimi 官方 Anthropic 兼容端点可用（ANTHROPIC_BASE_URL），但属于"协议兼容层"路径，高级特性依赖兼容层实现进度。

### 3.4 踩坑排错（权重 10）
OAI/PAI 层薄、报错一眼到底（PAI 因 v1/v2 教程断层各扣一点）；LC 异常栈穿 langchain-core/langgraph 内部、多包版本要对齐、deprecation 警告噪音；CAS 出问题要区分 SDK / 兼容层 / 模型 / 子进程引擎四方责任。

### 3.5 流式与 FastAPI（权重 10）
OAI：`Runner.run_streamed()` 产出类型化事件流直接映射 SSE，全异步与 FastAPI 同构，官方 cookbook 有完整实例。PAI：`run_stream` + 官方 FastAPI/Vercel UI 事件流文档（pydantic.dev/docs/ai/integrations/ui/overview）。LC：`astream` 多模式概念偏多。CAS：流式可接但子进程引擎放进 Web 服务偏重、官方 FastAPI recipe 少。

### 3.6 多 Agent（权重 10，按"演示里的一段"定位评分）
需求形状：分工（并行 fan-out）+ 1 轮 review + 辩论（≤2 轮）+ 汇总。
- LC 10：supervisor 官方参考实现、Send API 动态并行、checkpointer、辩论是成熟已知模式——全是框架原生。
- OAI 7：agents-as-tools（主控保留控制权）与"分工-汇总"天然同构；并行 asyncio.gather 有官方 cookbook；辩论循环自己写约 30 行。
- CAS 8：subagents/fork 原生且强，但 harness 式的子代理对我们偏重。
- PAI 6：agent-as-tool + v2 SubAgents capability 可实现，但多 Agent 配方/示例最少，Harness 仍 0.x。
若把多 Agent 定位改成"核心卖点"（深辩论/人审/中断恢复），本维度对 LC 应加权重估，见第四节。

### 3.7 MCP/插件（权重 8）：见第二节。
### 3.8 会话状态（权重 8）：OAI 内置 SQLiteSession（与选型天然对齐）；CAS session 强；PAI 手动 ~20 行；LC 中间件或手传。
### 3.9 版本风险（权重 7）：LC 1.x semver 最稳；PAI v2 承诺期但发版飞快（10 天 6 版）；OAI 0.24 周更、minor=breaking（官方文档明说）；CAS 0.x 与 Claude Code 版本强耦合。共同纪律：**锁死 requirements.txt，演示前禁升版本**。

| "多 Agent"从演示一段升级为核心卖点（10→20） | 翻倍 | **LC 升至第二**（约 81），逼近前两名 | LangGraph 的原生编排开始兑现价值 |

## 五、结论与决策规则（不变，但现在你知道为什么了）

1. **默认推荐 OAI SDK**：总分与 PAI 打平，但在"学生团队安全"相关维度（中文文档、AI 辅助通过率、内置会话、坑少且有文档解法）全面占优——这些正是两周课设最不能赌的。
2. **体验上限 PydanticAI**：组员读英文文档无障碍 + 愿意人工复核 AI 生成代码 → 选它，结构化输出和国产模型支持是四家最强。
3. **LangChain/LangGraph 只在一种情形下上位**：多 Agent 升级为核心卖点（复杂流转/人审/中断恢复），此时学习曲线值得付。
4. **Claude Agent SDK**：课题若是"会写代码/操作电脑的 Agent"它第一；我们的形态下它的 harness 能力是负资产。
5. **保底**：底座不动，换框架 ≈ 1 天。第一天用选定框架跑通"JD → 结构化 JSON" + 一次 MCP 搜索调用，实测定案。
